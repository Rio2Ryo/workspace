## Shiro Loop 停止・停滞

### 何が起きたか
- Yakonより「やっぱ何も進んでいないように見える」と指摘。
- 確認したところ、`shiro-loop-tick` と `shiro-loop-digest` の OpenClaw cron が disabled になっていた。
- tmux セッション自体は残っていたが、多くが `permission-wait` / `blocked` / `new task? /clear` で止まり、実作業の前進や承認パケット化が進んでいなかった。
- さらに両cronの `delivery.mode` が `none` で、動いても #白 に見える投稿が出ない設定だった。
- 07:27の自動投稿は `nudges=0` / `acted=false` だったにもかかわらず、「白がやること」「次回から」といった未実行の予定を進捗のように出してしまった。

### なぜ起きたか
- 監視 cron が disabled になっても自己検知・自己復旧する仕組みがなかった。
- `ops/shiro-loop-tick.mjs` の nudge 条件が狭く、`permission-wait` でも `next` が特定文言に一致しないと再投入されなかった。
- 結果として、観測結果は「待ち」として残るだけで、Claude Code 側へ「安全なローカル作業」「承認パケット化」「DONE確認文作成」を再投入できていなかった。
- digest 側が `last-report.json` の `acted=true` を見ず、state/digest上の予定をそのまま人間向け報告に変換していた。

### 次回どう防ぐか
- `shiro-loop-tick` / `shiro-loop-digest` cron を即時 enabled に戻した。
- `ops/shiro-loop-tick.mjs` を修正し、`permission-wait` の `external-action` / `needs-yakon` / `done-signoff`、および `blocked` を再投入対象にした。
- 手動で `node ops/shiro-loop-tick.mjs --act --json --nudge-cooldown-minutes 0 --max-nudges 14` を実行し、13セッションへ再投入した。
- `shiro-loop-tick` / `shiro-loop-digest` の `delivery.mode` を `announce` に変更し、送るべき内容がある場合は #白 に投稿されるようにした。
- `ops/shiro-loop-digest.mjs` を修正し、`last-report.json` の `acted=true` / `kind=nudged` のみを「実行したこと」として表示するようにした。未実行は「未実行の整理待ち」と明示する。
- 09:01 JST、Yakonより「各スレッドに発言しただけで何も動いていない」と指摘。確認すると、`kind=nudged` / `acted=true` を digest が「実行したこと」に分類していたため、再投入や確認送信だけが進捗に見えていた。`ops/shiro-loop-digest.mjs` を修正し、再投入は「再投入しただけで、まだ成果未確認」に分離。`ops/message-quality-check.mjs` に「実行したこと: セッションへ確認を送信/再投入」を失敗扱いにするガードを追加した。

### ルール反映
- 「cronがdisabled」「最終runが期待間隔を超過」「permission-waitが3件以上でnudges=0」のいずれかを検知したら、報告だけでなく自己修復・再投入を先に行う。
- 監視/報告cronは `enabled=true` だけでなく、`delivery.mode=announce` または明示的な投稿経路があるかも確認する。
- Yakonへの報告では「動いていないように見える」ではなく、実際の停止要因、復旧済み操作、残っている制約を短く出す。
- 「やる」「次回から」「白がやること」「tmux/セッション再投入」「確認送信」は進捗扱いしない。進捗として出してよいのは、成果が観測できた実コマンド結果、検証結果、commit、push/deploy結果、スレッド内の具体的な完了/ブロッカー更新だけ。再投入は必ず「成果未確認」と明示する。

- X/ウェブ調査では、Claude Code/Codex等の長時間自律運用は「Auto modeに任せる」だけではなく、HITL承認、durable workflow、観測ログ、eval/verification、承認UI/キューを組み合わせる流れが主流だった。

- 進捗報告は `result_observed=true` の時だけ。`nudged/sent/reminded` は成果ではなく未確認。

### ルール反映
- 自律性を上げるにはプロンプト強化ではなく、ワークフロー制御、承認キュー、観測可能な結果、品質ゲートを実装する。

- 13:36 JST、Yakonより「まだだめだよね、どうしたらいいの！」と指摘。原因は、`approvalPacket.ready` が証拠行のプロンプト記号で false になり、確認依頼が出なかったこと、さらに `threadId` 欠落と `needs_session` を白が報告するだけで実行していなかったこと。修正として、承認可否判定は exact action を主に見て evidence のプロンプト記号では落とさない、`ops/session-thread-overrides.json` で既知session/threadを補完する、`needs_session` 9件はtmux+Claudeを実際に起動する、実体のない previous workflow は復元しない、思考中Claudeを blocked と誤判定しないよう controller を修正した。今後 `needs_session` は報告項目ではなく白の実行項目。`approvalReady>0` かつ `readyToSend=false` は台帳不備として即補正する。
