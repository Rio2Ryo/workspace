## Sora-VPS2 Hermes / gpt-5.5 Codex stream TypeError
1. 何が起きたか: Yakonさんが `#sora-hermes` で `Sora-VPS2` に確認したところ、`Non-retryable error (HTTP None)` / `'NoneType' object is not iterable` が再発した。
2. なぜ起きたか: `ssh sora` 上の `sora-hermes` Hermes gateway は起動していたが、`openai-codex` / `gpt-5.5` の Codex stream request 直後に `TypeError: 'NoneType' object is not iterable` で落ちていた。Discord接続やtmux停止ではなく、gpt-5.5 Codex stream経路側の不具合。
3. 対応: `/root/.hermes/config.yaml` の `model.default` を `gpt-5.5` から `gpt-5.4` に変更し、`sora-hermes` だけを外部SSHから再起動。新しい起動コマンドは `--replace` を外した。ログで `Connected as Sora-VPS2#5856` と `Gateway running with 1 platform(s)` を確認。
4. 次回どう防ぐか: Sora-VPS2で同じ `NoneType` が出たら、まず `ssh sora 'tail -n 180 /root/.hermes/logs/sora-hermes-gateway.log'` を確認する。`gpt-5.5` の Codex stream直後なら、再起動だけでなく `config.yaml` のモデルを安定版へ落としてから再起動する。
5. 例外時に確認する条件: `gpt-5.5` に戻す必要がある場合、または Hermes / Codex provider自体の更新・本番常駐方式変更を行う場合はYakonさんへ確認する。

## Sora-VPS2 Hermes / Codex provider full bypass
1. 何が起きたか: `gpt-5.4` へ落としても `openai-codex` の Codex stream request が `'NoneType' object is not iterable` で落ち続けた。
2. なぜ起きたか: Hermes の `responses.stream()` だけでなく `responses.create(stream=True)` フォールバックでも同じ TypeError が発生したため、モデル差ではなく Sora VPS の `openai-codex` provider経路全体の不具合と判断した。
3. 対応: VPSの `/root/.bashrc` にあった `GEMINI_API_KEY` を `/root/.hermes/.env` に反映し、Hermes本体設定を `provider: gemini` / `default: gemini-3-flash-preview` / `base_url: https://generativelanguage.googleapis.com/v1beta` に変更。`hermes -z 'Reply with exactly: ok' --provider gemini -m gemini-3-flash-preview --ignore-rules` で単体疎通OK。壊れたDiscordセッション `20260531_063058_8b533574` を削除し、`sessions.json` の `#sora-hermes` 紐付けも削除して新規会話へ戻した。
4. 次回どう防ぐか: Sora-VPS2の `openai-codex` が同じ `NoneType` を出す場合、モデル変更だけで粘らず providerを切り替える。切り替え後は古い失敗セッションの自動resumeが残っていないか `hermes sessions list` と `/root/.hermes/sessions/sessions.json` を確認する。

## tmux Web View session/thread mapping drift
1. 何が起きたか: Yakonさんから `tmux-web-view` の全セッションとDiscordスレッドの対応確認を依頼された。live tmux session と `NEXT_PUBLIC_TMUX_TARGETS_JSON` / `NEXT_PUBLIC_TASK_SESSION_MAP_JSON` に複数のズレがあった。
2. なぜ起きたか: 2026-05-25前後に tmux session と thread 名をアプリ名へリネームしたが、viewer側のproduction envに古い `hermes-jp` / `codex-goal` / ontrust親チャンネル向けIDが残っていた。さらに shiro/panai/gohanai/sora の表示対象と実feed対象が同期されていなかった。
3. 次回どう防ぐか: tmux sessionをrenameしたら同時に `NEXT_PUBLIC_TMUX_TARGETS_JSON` と `NEXT_PUBLIC_TASK_SESSION_MAP_JSON` を更新し、`/api/sessions` のlive一覧・Discord `channel-info`・検索結果で thread ID を突合する。本番env変更前に差分表を出す。
4. ルールへの反映: Web Viewの表示対象は「live session名」「thread名」「thread ID」の3点セットで管理し、汎用名 `claude` / `codex` は親チャンネル運用か専用thread運用かを明示する。
